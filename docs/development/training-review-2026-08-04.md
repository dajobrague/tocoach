## HIGH (9)

### [FIXED] Server transform maps paused programs to "completed", killing the entire paused/reactivate feature
- **Where:** `lib/utils/training-utils.ts:384` — areas: trainer-programa, api-trainer, api-client, regression-diff (4 independent reports)
- **What:** transformToWorkoutProgram returns status: clientProgram.status === "active" ? "active" : "completed". Commit 47bd2db widened WorkoutProgram.status to include "paused"/"cancelled" and made fetchPrograms fetch all statuses, but the GET route (app/api/clients/[clientId]/programs/route.ts:269) still runs every row through this transform, so a client_programs row with status "paused" reaches the client as "completed". In features/trainer/training/programa/programa-section.tsx:52-55 pausedPrograms = programs.filter(p => p.status === "paused") is therefore always empty: the new "Pausados" dropdown section never renders, and the "Activar" button in program-header-card.tsx:194 (gated on program.status === "paused") is unreachable. The feature the commit ships is entirely non-functional.
- **Failure:** Trainer pauses a program via the header chip -> PATCH sets client_programs.status='paused' -> refetch returns the program transformed with status 'completed' -> it is filtered out of both activePrograms and pausedPrograms -> the program disappears from the selector with no 'Pausados' section and no way to reactivate it (if it was the only program, the empty state 'Este cliente no tiene programa activo' shows). Exactly the pre-commit vanishing bug, unchanged.

### classifyDay marks a barely-started day 'complete' when zero exercises reached their set count
- **Where:** `components/dashboard/client-profile/tabs/microcycle/adherence.ts:201` — areas: trainer-seguimiento
- **What:** Inside the `loggedSetsTotal > 0` branch, if `completedExercises >= totalPrescribed` fails and `completedExercises > 0` fails, the code falls through to `return "complete"`. With a prescription present, `computeDayAdherence` only counts an exercise as completed when its logged set count reaches the prescribed count, so a day where the client logged fewer sets than prescribed on every touched exercise has loggedSetsTotal > 0 and completedExercises === 0 — and is classified 'complete' ('Hecho', green chip in week strip, month grid and session card). Meanwhile a client who fully completed 1 of 3 exercises gets 'partial' ('Empezado'). Doing less work yields a better classification than doing more, and the test suite only covers the completedExercises=1 case.
- **Failure:** Session prescribes Press banca 4 sets (matching logs exist so computeDayAdherence is used). Client logs 2 of the 4 sets and stops (or is mid-session today); scheduled_sessions.status is still 'scheduled'. computeDayAdherence → completedExercises=0, loggedSetsTotal=2. classifyDay(true, adherence, false, false) → falls through to 'complete'. Trainer's Seguimiento shows the day as 'Hecho' (green) though the client did half of one exercise; if the client instead finishes all 4 sets of one of two prescribed exercises, the day shows only 'Empezado'.

### Range reps prescription renders blank but silently saves lower bound
- **Where:** `components/client-dashboard/exercise-log/exercise-set-row.tsx:78` — areas: client-exercise-log

### DELETE program cascade deletes sessions/exercises without any trainer ownership check
- **Where:** `app/api/clients/[clientId]/programs/route.ts:828` — areas: api-trainer
- **What:** The DELETE handler fetches sessions filtered only by program_id (line 819-822), then deletes session_exercises (line 828-831), scheduled_sessions (852-855) and sessions (867-870) with no trainer_id filter. Only the final client_programs and programs deletes are trainer-scoped, and deletes matching zero rows are not errors, so the handler returns success. RLS grants anon full access (`"Allow anon to manage session exercises/sessions" ... USING (true)`), so nothing at the DB level blocks the cross-tenant delete.
- **Failure:** Any authenticated trainer from any tenant calls DELETE /api/clients/<anything>/programs?programId=<another trainer's program UUID> → all of that program's sessions, session_exercises and scheduled_sessions are permanently deleted (the victim's program shell remains but is emptied), and the attacker gets {success:true}. Requires knowing the UUID, but it is irreversible cross-tenant data loss with no ownership check.

### PUT/DELETE session_exercises are not scoped to the authenticated trainer
- **Where:** `app/api/clients/[clientId]/programs/[programId]/sessions/[sessionId]/exercises/route.ts:397` — areas: api-trainer, security (2 independent reports)
- **What:** PUT fetches the session_exercise without any trainer filter (line 272-276) and updates it with only `.eq("id", sessionExerciseRowId)` (line 394-398); DELETE (line 464-467) likewise deletes purely by id. Sibling handlers (POST here, sessions PUT/DELETE, duplicate routes) all verify trainer_id; these two do not, and RLS is `anon USING (true)` so there is no DB-level guard. The URL's clientId/programId/sessionId params are ignored (`params: _params`).
- **Failure:** A trainer of tenant B who obtains a session_exercises UUID from tenant A calls PUT .../exercises?exerciseId=<uuid> with arbitrary sets/reps/metadata → tenant A's prescription is overwritten (or repointed via exerciseId swap to an exercise from B's library, which passes the swap validation because that check uses the ATTACKER's trainer_id). DELETE with the same UUID removes the slot entirely. Victim's client sees a corrupted or missing exercise.

### PUT session_exercise mutates row without verifying it belongs to the trainer
- **Where:** `app/api/clients/[clientId]/programs/[programId]/sessions/[sessionId]/exercises/route.ts:396` — areas: security
- **What:** The PUT handler fetches the session_exercise by id only (`.eq('id', sessionExerciseRowId).single()`, line 274-276) selecting session_id but never checking `sessions.trainer_id === session.trainer_id`, then updates with `.update(updateData).eq('id', sessionExerciseRowId)` (line 396-397) again with no trainer/tenant scope. - **Where:** `app/api/clients/[clientId]/programs/route.ts:710` — areas: api-trainer
- **What:** PUT constructs metadata from scratch ({type, sessions_per_week, category?, goal?/division?}) and overwrites the column. The inline-rename flow sends `programToUpdateInput(selected)` which cannot supply `goal` because transformToWorkoutProgram never exposes it in the GET payload (acknowledged in programa-format.ts:167 as a limitation). So any rename or header-card edit of a cardio program drops the stored goal permanently; defaults also overwrite (division falls back to "Full Body" for strength programs that had none).
- **Failure:** Trainer creates a cardio program with goal='resistencia', later renames it inline → PUT writes metadata {type, sessions_per_week, category:'cardio'} without goal → goal is permanently lost from the database and no longer shown anywhere the goal is read.

### Legacy dedup lookup ignores maybeSingle's multiple-rows error and inserts duplicate logs
- **Where:** `app/api/clients/[clientId]/exercise-logs/route.ts:312` — areas: api-trainer
- **What:** The 3-key dedup lookup (scheduled_session_id + exercise_id + client_id, used when the body has no sessionExerciseId) calls `.maybeSingle()` but destructures only `data`, discarding `error`. When a session has two slots of the same exercise (rows differentiated by session_exercise_id — the exact case the slot-attribution feature created), maybeSingle returns an error with data=null, so the code takes the insert path instead of updating.
- **Failure:** Client's session contains the same exercise in two slots and logs were saved with sessionExerciseId; the client later saves from a stale PWA bundle (service-worker pinning is a known risk in this app) that omits sessionExerciseId → every autosave inserts a NEW exercise_logs row instead of updating → duplicate logs inflate volume/records for that day and the day can flip to "completed" off phantom coverage.

### scheduled_sessions query error silently discarded — failures render as a template/rest day
- **Where:** `app/api/client/scheduled-sessions/[date]/route.ts:134` — areas: api-client
- **What:** The GET destructures only `data` from the scheduled_sessions query (`const { data: ssRowsRaw } = await supabase...`) and never checks the error. On any query failure ssRows becomes [], so the handler skips the real-row path and falls through to the microcycle-template or rest-day response with success:true. The isYmd regex also accepts impossible calendar dates (e.g. 2026-02-31, 2026-13-05), which make this exact query error on the date cast, and diffDays then yields NaN so no slot matches — the endpoint answers success with a fabricated rest day instead of 400/500. The sibling routes (start/complete/state) surface their query errors as 500s; only this one swallows it.
- **Failure:** Client who trained session A on 2026-08-03 reopens that day while the scheduled_sessions query fails transiently (or any caller requests /api/client/scheduled-sessions/2026-02-31): the API returns success with source "template" or "rest", hiding the session the client actually trained (divergence render lost) or asserting a rest day for a nonexistent date, with no error signal for the UI to retry.

### "12+" bucket record ignores rep improvements at equal/lower weight, so RepMax.e1rm is not the bucket's best e1RM
- **Where:** `lib/training/e1rm.ts:141` — areas: lib-core
- **What:** computeRepMaxes decides a new record with `weightKg > current.weightKg` (tie broken only by earlier date). For buckets 1-11 reps are fixed, so weight ordering equals e1rm ordering — but in the "12+" bucket reps vary. A later set with the SAME weight and MORE reps (strictly higher e1rm) never replaces the record, and a set with slightly lower weight but far more reps never registers at all. The stored RepMax.e1rm/reps for "12+" therefore understate the client's real best. Downstream, features/trainer/training/progreso/progreso-format.ts#bestRepMax picks the max RepMax.e1rm and progreso-section.tsx renders it as "Mejor 1 RM relativo" — which can contradict `bestE1rm`/the chart peak computed from the very same payload (buildProgression). diffRecords (line 189, same weight-only rule) also suppresses the PR toast/banner for these rep-PRs.
- **Failure:** Client does rep progression at fixed dumbbells (very common for accessories): day 1 = 10 kg × 12 (e1rm 14 kg), day 30 = 10 kg × 24 (e1rm 18 kg). computeRepMaxes keeps {bucket "12+", 12 reps, e1rm 14, day 1} because 10 kg is not > 10 kg; diffRecords returns null so no PR is celebrated. On the trainer Progreso screen the chart peaks at 18 kg while the "Mejor 1 RM relativo" stat shows 14 kg from the same response — internally inconsistent, and the record chip shows "12+ RM · 10 kg" dated day 1 with the inferior 12-rep set.

### exercise-logs POST does not verify the posted sessionId belongs to the client's tenant
- **Where:** `app/api/clients/[clientId]/exercise-logs/route.ts:205` — areas: security
- **What:** The POST handler looks up the session by the client-supplied `sessionId` (`.from('sessions').select('trainer_id, tenant_host').eq('id', sessionId).single()`, lines 201-205) and then propagates `sessionData.tenant_host` and `sessionData.trainer_id` straight into the upsert_scheduled_session RPC and the exercise_logs insert, without checking that the session's tenant_host matches the authenticated client's tenant. The sibling routes explicitly added this guard: /scheduled-sessions/[date]/start (lines 73-83) and /complete (lines 111-121) both reject when `sessionData.tenant_host !== tenant.host` with the comment 'sin esto un sessionId ajeno crearía filas con tenant_host de otro tenant'. This route (and the older /scheduled-sessions POST) omit it.
- **Failure:** An authenticated client passes a sessionId belonging to a different tenant. The code creates scheduled_sessions and exercise_logs rows stamped with the FOREIGN tenant_host and the foreign trainer_id (but the client's own client_id), injecting cross-tenant rows into another tenant's data space — the exact scenario the /start and /complete routes were patched to prevent.

## Known limitations accepted (flagged by verifiers, documented deliberately)

- **DELETE program retry after partial cascade failure**: if a previous cascade failed mid-way after removing the client_programs row, a retry now 404s at the ownership gate and the orphaned programs row is not deletable via this endpoint. Requires a mid-cascade DB failure to arise; true transactional cascade (RPC) is the eventual fix.
- **Stale metadata.goal key after category change**: the PUT metadata merge never deletes keys, so switching a program cardio→strength leaves an inert goal key behind. Readers branch on category; no visible effect.
- **Legacy logs + duplicate same-exercise slots**: logs without session_exercise_id collapse onto the first pending duplicate slot, so a fully-completed day logged pre-backfill can read "partial". Trades the old false-complete for rare under-credit; disappears as legacy logs age out.
- **>2000 all-time logs**: the trainer exercise-logs fetch now orders DESC before the 2000-row cap (then re-reverses), so a long-tenured client loses the oldest tail, never recent history.
- **"12+" rep-PR toast copy**: a same-weight rep improvement in the 12+ bucket shows identical weights ("antes 10 kg") because toast/banner lines don't carry reps. Data is correct; copy could be enriched later.
